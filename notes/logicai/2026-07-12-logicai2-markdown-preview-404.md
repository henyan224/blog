# 技术专题：LogicAI2 Markdown 预览 404 的定位与修复

> 状态：草稿，待萧何审计。本文仅用于知识沉淀流程测试，暂不迁移到正式 Blog 文章目录。

## 问题现象

在 LogicAI2 前端中，文件树可以看到 Markdown 文档，但点击在线查看时，请求返回：

```text
404 not found
```

用户侧表现为：

- 前端工作区已经选中某个项目目录；
- 文件树可以正常列出 `.md` 文件；
- 点击文档预览或打开文件内容时失败；
- 失败集中在通过前端接口读取 Markdown 内容的链路上。

这个问题容易误判为 Blog 仓库静态页面、Markdown 渲染组件或文件本身不存在的问题，但实际故障点在 LogicAI2 的前后端文件读取链路。

## 排查过程

### 1. 先校准真实问题域

初始排查时，需要区分两个不同仓库/系统：

- Blog 仓库：负责公开文章和静态页面展示；
- LogicAI2：负责多角色 Agent 系统、前端工作台和本地文件访问。

本次故障发生在 LogicAI2 前端，不是 Blog 页面构建或部署问题。因此排查对象应切换到 LogicAI2 的前端和后端接口。

### 2. 检查前端文件树与文件读取接口的路径语义

文件树展示时，前端拿到的是相对于当前 workspace 的路径。也就是说，用户在 UI 中看到并点击的文件路径，并不是一个天然可由进程当前目录直接读取的绝对路径。

需要确认：

- 当前选中的 workspace 是什么；
- 文件树展示路径是否相对 workspace；
- `/api/file` 读取文件时是否使用了同一个 workspace；
- 前端请求是否正确打到 LogicAI2 后端，而不是被 Vite dev server 或其他服务错误处理。

### 3. 检查开发环境代理链路

在 Vite 开发环境中，前端页面和后端 API 可能运行在不同端口。若 `/api` 请求没有正确代理到 LogicAI2 后端，即使后端接口本身正确，也可能在开发服务器层面得到 404。

因此除了后端文件读取逻辑，还需要检查开发服务器配置。

## 根因

本次问题有两个关键点：

### 根因一：文件路径缺少 workspace 上下文

前端文件树使用的是“相对于当前 workspace 的路径”，但后端 `/api/file` 在读取文件时没有正确使用当前 workspace 作为根目录。

结果是：

```text
前端点击：docs/example.md
后端读取：未按当前 workspace 拼接 docs/example.md
最终结果：目标文件定位失败，返回 404
```

多 workspace 系统中，单独的相对路径没有完整语义。它必须和“当前 workspace 根目录”一起使用，才能定位真实文件。

### 根因二：开发环境 `/api` 代理需要校准

在 Vite dev 场景下，前端请求 `/api/file` 需要代理到 LogicAI2 后端服务。若代理配置不完整，前端请求可能不会进入正确的后端处理逻辑，从而表现为接口 404。

## 修复点

以下路径以 LogicAI2 仓库根目录为基准。本次修复涉及两个关键文件：

```text
src/adapters/web/index.ts
web/vite.config.ts
```

### 1. 后端文件读取逻辑

修复位置：

```text
src/adapters/web/index.ts
```

修复方向：

- `/api/file` 接口读取文件时，应基于当前选中的 workspace 解析目标路径；
- 不应假设请求参数中的文件路径可以直接相对于进程工作目录读取；
- 需要保证文件读取边界限制在 workspace 内，避免路径语义混乱或越界访问。

### 2. Vite 开发代理配置

修复位置：

```text
web/vite.config.ts
```

修复方向：

- 开发环境下将 `/api` 请求代理到 LogicAI2 后端服务；
- 确保前端点击 Markdown 预览时，请求进入真实后端接口；
- 避免 Vite dev server 自身返回 404。

## 经验教训

### 1. 多 workspace 系统中，路径必须带归属

在单项目应用里，一个相对路径通常默认相对于项目根目录。但在多 workspace 系统中，同一个相对路径可能对应不同项目：

```text
docs/README.md
```

它只有在绑定 workspace 后才有确定含义：

```text
{workspace}/docs/README.md
```

因此接口设计中应显式传递或解析 workspace 上下文，不能让前端和后端各自假设路径根目录。

### 2. “文件存在”不等于“接口能读取”

文件树能展示文件，只能说明“列目录链路”正常；文件预览能打开，则依赖另一条“读取文件内容链路”。两条链路可能使用不同接口、不同路径解析方式、不同代理配置。

排查时要拆开看：

- 列目录是否成功；
- 前端点击时发出的请求是什么；
- 请求是否到达正确后端；
- 后端解析出的真实路径是什么；
- 文件读取是否被权限或边界检查拦截。

### 3. 前端代理也是业务链路的一部分

开发环境中的代理配置不是“外围细节”。当前端页面通过 `/api/file` 访问后端时，Vite proxy 是否正确，直接决定请求能否抵达业务服务。

如果只看业务代码，不看开发服务器代理，很容易漏掉一类 404。

### 4. 仓库边界需要先校准

本次问题曾容易被误判到 Blog 仓库。对于同时维护多个相关仓库的系统，排查前必须先确认：

- 故障发生在哪个运行中的系统；
- 用户看到的页面属于哪个仓库；
- 当前命令、文件读写是否在正确目录。

这类校准比直接修改代码更重要。
